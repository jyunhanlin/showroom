## TL;DR

- 這一課講 WebGPURenderer 的後製。舊版的 `PostProcessing` 類別改名成 `RenderPipeline`，render loop 裡的 `renderer.render()` 換成 `renderPipeline.render()`。
- `pass(scene, camera)` 把場景畫進一張貼圖。之後每一步都是 `renderPipeline.outputNode = f(renderPipeline.outputNode)`，吃上一個、吐新的。
- 內建的 pass 都是一個 node：`bloom()`、`chromaticAberration()`、`sobel()`、`fxaa()`、`pixelationPass()`。從 `three/addons/tsl/display/` import。
- `bloom()` 只回傳光暈，要 `.add()` 回原圖。
- `pixelationPass()` 自己 render 場景，所以它取代 `pass()`，不是接在後面。
- MRT：`scenePass.setMRT(mrt({ output, normal: normalWorld }))`。一次 render 同時寫出顏色和法線，再用 `getTextureNode('normal')` 拿出來給 `sobel()`。
- Tone mapping 也算後製。FXAA 要吃 tone mapping 之後的顏色，所以設 `outputColorTransform = false`，自己在 FXAA 前面放 `renderOutput()`。
- 要讀「別的像素」才需要真的貼圖，用 `convertToTexture()`。只改同一個像素的顏色，node 直接串就好。
- 自訂 pass 照 three 的慣例寫：一個 `TempNode` 子類別加一個小寫的工廠函式，參數過 `nodeObject()`，給預設值。
- Shatter：voronoi 切片，`step()` 在邊上畫裂縫，cell ID 乘黃金角決定每片往哪偏。`progress` 一個值同時推動裂縫粗細和偏移距離。

## 為什麼每一步都寫 outputNode = f(outputNode)

```js
const renderPipeline = new THREE.RenderPipeline(renderer);

// Scene pass
const scenePass = pass(scene, camera);
renderPipeline.outputNode = scenePass;

// Bloom pass
const bloomPass = bloom(renderPipeline.outputNode);
renderPipeline.outputNode = renderPipeline.outputNode.add(bloomPass);

// Chromatic aberration pass
const chromaticAberrationPass = chromaticAberration(renderPipeline.outputNode, 2, vec2(0.5), 1);
renderPipeline.outputNode = chromaticAberrationPass;
```

`outputNode` 是 pipeline 最後要畫上螢幕的那個 node。每一段都讀它、包一層、寫回去，下一段不用知道上一段的變數叫什麼。註解掉任何一段，前後自動接起來。課程整堂就是這樣開開關關試效果。

寫成 `bloom(pass(scene, camera))` 一行也行，結果一樣，只是不好拆。

`RenderPipeline` 不用處理 resize。它跟著 renderer 的尺寸走。

`bloom()` 回傳的只是光暈那張貼圖，所以要 `.add()` 回原圖。`chromaticAberration()` 回傳的是整張處理過的畫面，直接取代。每個 pass 回傳什麼不一樣，要看它的範例。

`chromaticAberration()` 後面三個參數：顏色分開多遠、從哪一點往外分（`vec2(0.5)` 是畫面中心）、紅綠藍之間的縮放差（`1` 就是不要）。

Bloom 的 `threshold` 和 `strength` 本來就是 uniform，改 `.value` 就好，不用重建。

## 為什麼 pixelationPass 要放在最前面

其他 pass 收的是 `outputNode`，`pixelationPass(scene, camera, 20, 2, 1)` 收的是場景和相機。它自己 render 一次，還用 MRT 拿法線和深度來畫邊。

所以它不是「接在後面的濾鏡」，而是「另一種 scene pass」。接在 bloom 後面，前面的效果全部不見。要用就取代 `pass()`，放在第一格。

## 為什麼 MRT 比較快

MRT 是 Multiple Render Targets。一次 render，每個 fragment 同時寫進好幾張貼圖，每張寫不同的東西：

```js
const scenePass = pass(scene, camera);
scenePass.setMRT(mrt({
  output: output,
  normal: normalWorld,
}));
renderPipeline.outputNode = scenePass.getTextureNode('output');
```

- `output` 是 material 原本要輸出的顏色。
- `normal` 是世界座標的法線。
- 名字自己取，`getTextureNode('normal')` 就拿得到。

舊作法要換一套 material 把整個場景再畫一次，才拿得到法線。MRT 只畫一次。

`sobel()` 是邊緣偵測。直接吃畫面，材質上的紋路也會被當成邊，線到處都是。改吃法線，只剩形狀的邊：

```js
const sobelPass = sobel(scenePass.getTextureNode('normal')).remapClamp(0.2, 1, 0, 1);
renderPipeline.outputNode = renderPipeline.outputNode.add(sobelPass);
```

`remapClamp(0.2, 1, 0, 1)` 把 0.2 以下壓成 0。曲面上法線慢慢變，也會被抓成淡淡的邊，這一步把它們去掉。

地板和天空不想要邊，就在它們的 material 上蓋掉預設的 MRT：

```js
sky.material.mrtNode = mrt({
  output: output,
  normal: vec4(1),
});
```

`setMRT()` 是全場景的預設，`material.mrtNode` 是單一 material 的覆寫。法線寫成一片純白，sobel 在上面找不到邊。

## 為什麼 tone mapping 要手動放在 FXAA 前面

`RenderPipeline` 預設在最後一格之後自動加 tone mapping 和 sRGB 轉換。`RenderPipeline.js` 第 194 行是 `outputNode = renderOutput( outputNode, toneMapping, outputColorSpace )`。畫的時候再把 renderer 的 `toneMapping` 暫時改成 `NoToneMapping`（第 141 行），免得套兩次。

所以 pipeline 裡的每一格看到的都是 linear、還沒 tone map 的顏色。Bloom 要的就是這個：亮度可以超過 1。

FXAA 不一樣。它找的是「看起來」對比強的地方，要吃最後上螢幕的顏色才準。所以：

```js
renderPipeline.outputColorTransform = false;

// ...

// Color transform pass
renderPipeline.outputNode = renderOutput(renderPipeline.outputNode);

// FXAA pass
const fxaaPass = fxaa(renderPipeline.outputNode);
renderPipeline.outputNode = fxaaPass;
```

關掉自動轉換，自己把 `renderOutput()` 放在 FXAA 前面。關掉之後，pipeline 把 renderer 的 `toneMapping` 和 `outputColorSpace` 放進 context（第 198 行），`renderOutput()` 不給參數就從那裡拿（`RenderOutputNode.js` 第 119 行）。所以改 renderer 的設定，這裡照樣跟著變。

為什麼還要 FXAA：renderer 的 `antialias: true` 是 MSAA，只處理幾何的邊。課程在地板上畫一條條黑白直線，線和線之間的鋸齒在同一個三角形裡面，MSAA 管不到。FXAA 看的是整張畫面，哪裡都能處理。

## 為什麼 shatter 要 convertToTexture()

課程先寫了一個小的 Drunk pass：

```js
const drunkTexture = convertToTexture(renderPipeline.outputNode);
const waveUv = vec2(
  uv().x,
  uv().y.add(uv().x.add(time.mul(0.2)).mul(7).sin().mul(0.1)),
);
renderPipeline.outputNode = texture(drunkTexture, waveUv).mul(color('aquamarine'));
```

只乘 `color('aquamarine')` 不用貼圖。那只是在同一個像素上多接一個 node，和前後的 node 編進同一支 fragment shader。

波浪不一樣。這個像素要顯示「旁邊那個像素」的顏色，前面的結果就得先存成一張真的貼圖，才能用 `texture()` 去別的座標取。Shatter 的 `offsetUv` 也是同一件事。

`convertToTexture()` 會先看手上有沒有現成的貼圖（`RTTNode.js` 第 363 行）：

- 已經是貼圖，原樣回傳。
- 是 `pass()`，回傳它的 `getTextureNode()`。
- 其他才用 `rtt()` 多開一張 render target。

Demo 的 shatter 直接接在 `pass()` 後面，所以沒有多開 render target。要讀別的像素才付這個代價，這是課程結尾說的效能優勢。

Demo 拿掉 `convertToTexture()` 試過：畫面全黑，Console 印 `` `texture( value )` function expects a valid instance of THREE.Texture() ``。

## 為什麼 voronoi 要除以最長邊

```js
const viewportMaxSide = max(viewportSize.x, viewportSize.y);
const voronoiUv = viewportCoordinate.div(viewportMaxSide);
const voronoiColor = voronoi(voronoiUv, this.subdivision, this.seed);
```

用 `uv()` 或 `viewportUV`，x 和 y 都是 0 到 1。畫面是長方形，cell 就被拉扁。

`viewportCoordinate` 是像素座標，兩軸同一個單位。兩軸除以同一個數，cell 就不會變形。除以最長邊，長邊剛好 0 到 1，`subdivision` 永遠是長邊上大約幾片。

課程的 `voronoi()` 是課程附的 `voronoi.js`，回傳一個 vec4：

- `.r`：到這片中心點的距離。
- `.g`：到邊的近似距離。便宜，有點不規則，看起來反而自然。
- `.b`：到邊的精確距離。這一課沒用到。
- `.a`：這片的 ID，一片一個整數，片內每個像素都一樣。

three 內建的 `mx_worley_noise_float()` 也是 voronoi，但沒有 ID，所以課程不用它。Demo 的 `voronoi()` 是另外寫的，照同樣的格式回傳。`.g` 用「第二近減最近」，沒算 `.b`。ID 是格子座標的 `x × 100 + y`，不像課程那樣一片接一片編號，但一片一個整數這點一樣。

## 為什麼裂縫是 step()

```js
const cracksNoise = mx_noise_float(voronoiUv.mul(5)).remap(-1, 1, 0, 0.5);
const cracks = voronoiColor.g.step(this.progress.sub(cracksNoise).mul(this.thickness));
```

`.g` 在邊上是 0，愈往中間愈大。`g.step(edge)` 是「`g` 大於等於門檻就是 1」，所以片的中間是 1，離邊比門檻近的地方是 0。門檻愈高，0 的那條帶子愈寬，裂縫就愈粗。

門檻是 `(progress − cracksNoise) × thickness`：

- `progress` 是 0 到 1 的進度。
- `thickness` 把它縮到合理的粗細。拆成兩個值，`progress` 才能乖乖停在 0 到 1。
- `cracksNoise` 讓裂縫不要同時出現。noise 高的地方要 `progress` 更大才開始裂。

`remap(-1, 1, 0, 0.5)` 把 noise 從 -1 到 1 搬到 0 到 0.5。直接用的話，一半是負的，減負數等於加，那些地方 `progress` 為 0 就已經裂了。

## 為什麼偏移方向用黃金角

```js
const goldenRatio = sqrt(5).add(1).div(2);
const goldenAngle = goldenRatio.mul(TWO_PI);
const angle = voronoiColor.a.mul(goldenAngle);
const offset = vec2(angle.cos(), angle.sin()).mul(this.progress);
const offsetUv = viewportUV.add(offset.mul(this.offsetStrength));
```

每片要一個方向，而且方向最好不要重複。ID 是整數，隨便乘一個角度會出事：乘 60°，每 6 號就轉回同一個方向。

乘黃金角，每多一號轉一個黃金角。黃金比例是無理數，轉再多號都不會轉回同一個方向。而且它是最難用分數逼近的數，新的方向總是落在已有方向之間比較大的空隙，所以整圈平均散開。向日葵的種子就是這樣排的。

`offset` 乘 `progress`，所以 `progress` 為 0 時完全不偏。`offsetStrength` 另外控制最大偏移。課程也說它和 `progress` 重複了，這是 API 的選擇：只有 `progress` 要做動畫，其他設好就不動。

最後一步：

```js
return mix(cracksColor, texture(this.textureNode, offsetUv), cracks);
```

`cracks` 為 0 取橘色，為 1 取偏移後的畫面。`cracksColor` 是 `_color.mul(colorStrength)`，`colorStrength` 為 3，亮度超過 1。Bloom 放在 shatter 後面，這些超過門檻的橘色就會暈開。Tone mapping 之後，最亮的地方也不會死白。

```js
) => new ShatterNode(convertToTexture(textureNode), nodeObject(subdivision) /* , … */);
```

內建的 `BloomNode` 和 `bloom()` 也是這個形狀。一個類別負責邏輯，一個小寫函式負責建立，別人拿來用跟用內建的一樣。

- `super('vec4')` 告訴 TSL 這個 node 輸出什麼型別。
- `setup()` 回傳這個 node 真正代表的 node graph。
- `TempNode` 會快取結果，同一個 node 被用兩次不會算兩次。
- `nodeObject()` 讓呼叫的人可以傳純數字，例如 `0.5`，進來都變成 node。
- 預設值用 `float()`、`int()`、`color()`，只丟一張畫面進來也有像樣的結果。

`seed` 用 `uniform(18, 'int')`，因為 voronoi 裡面的 `hash()` 要整數。傳 float 也會自動轉，只是多一步。

不想包類別也可以。課程結尾說，直接在外面對 `outputNode` 串 node 也能做到一樣的效果。類別是為了分享。

## 用例

- **一般的場景加光暈**：`pass()` 接 `outputNode.add(bloom(outputNode))`，threshold 調到只有燈和發光物超過。
- **卡通描邊**：MRT 寫法線，`sobel()` 吃法線，`remapClamp()` 去掉曲面上的淡邊。
- **某些物件不要描邊**：該 material 設 `mrtNode`，法線寫成 `vec4(1)`。
- **一次拿到好幾種資料**（法線、深度、自訂的 mask）：`setMRT()` 多加一個名字，不用再畫一次場景。
- **畫面扭曲、波浪、碎裂、折射**：`convertToTexture()` 之後，用改過的 UV 去 `texture()`。
- **只調色**（乘顏色、對比、飽和度）：直接串 node，不用 render target。
- **細條紋、細網格的鋸齒**：`outputColorTransform = false`，`renderOutput()` 之後接 `fxaa()`。
- **一群東西各自要不同的方向或顏色**：ID 乘黃金角。
- **做成可以分享的效果**：`TempNode` 子類別加工廠函式，參數過 `nodeObject()`，給預設值。

## Gotchas

- **`bloom()` 不是整張畫面**。它只回傳光暈，忘了 `.add()` 就只剩一片模糊的光。
- **`pixelationPass()` 接在後面，前面的效果全沒了**。它自己 render 場景，要放在第一格取代 `pass()`。
- **`.step()` 的參數順序跟函式版相反**。`x.step(edge)` 是 `step(edge, x)`，`MathNode.js` 第 1157 行的 `stepElement`。Node Functions 那課也踩過。
- **忘了 `convertToTexture()`，畫面全黑**。Console 印 `` `texture( value )` function expects a valid instance of THREE.Texture() ``。Demo 裡實際拿掉看到的。
- **FXAA 要放在 `renderOutput()` 之後**。預設的自動轉換加在最後一格之後，FXAA 會吃到 tone mapping 之前的顏色。
- **用顏色 debug 會被 tone mapping 騙**。課程把 cell ID 直接輸出成顏色，ID 大於 1 的片理應全白，卻還分得出深淺，因為 tone mapping 把超過 1 的值壓回來了。要看真實數值，先關 tone mapping。
- **`_color` 不叫 `color`**。`color` 是 TSL 的 node，同一個 scope 會撞名。課程用底線，demo 照用，所以加了一行 oxlint 例外。
- **R3F 寫法**：`useFrame(() => renderPipeline.render(), 1)`。priority 大於 0，R3F 就不再自己呼叫 `gl.render()`，由 pipeline 接手。
- **R3F 的 tone mapping 設在 `onCreated`**。R3F 只在第一次 configure 設 ACES，之後改成 Cineon 不會被蓋回去。`RenderPipeline` 每一幀比對 renderer 的 `toneMapping`，變了就重建輸出，所以 Inspector 的 `toneMapping` 選單在 `onChange` 裡直接改 `renderer.toneMapping` 就生效（demo 切成 None 實測過）。
- **Inspector 掛在建 pipeline 的同一個 effect 裡**。bloom 的兩個參數要 `bloomPass`，而 `bloomPass` 只在這個 effect 裡。掛載用 `attachInspector()`，它處理動態 import、SSR 和卸載，細節在 Patterns 那課的 Gotchas。
- **Demo 沒關 MSAA**。課程為了展示 FXAA，把 `antialias` 設成 `false`。Demo 用 R3F 的預設 `antialias: true`，`pass()` 的 render target 沿用 renderer 的 samples（`PassNode.js` 第 800 行），所以 MSAA 和 FXAA 都在。
- **Demo 的場景換掉了**。課程是一個鐵砧加天空，demo 換成幾個簡單的幾何體，燈光調暗，讓 bloom 主要打在裂縫上。Pipeline 只接課程最後的組合：`pass` → shatter → bloom → `renderOutput` → `fxaa`，MRT 和 sobel 沒接。
- **Pipeline 在同一個 `useEffect` 裡建立、也在它的 cleanup 裡 `dispose()`**，存進 ref 給 `useFrame` 用。分成 `useMemo` 建、另一個 effect 丟，StrictMode 跑「掛上、卸下、再掛上」時，`useFrame` 會拿到已經丟掉的 pipeline。在 Inspector 拉參數只改 uniform 的 `.value`，不重建。
